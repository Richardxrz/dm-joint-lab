# 审查包 01 · 定位与容量（10 个决定）

> 审查方式：逐条判「成立 / 不成立 / 改成 X」。判完才写代码。
> 每条格式：**决定 → 理由 → 依据 → 替代方案与代价 → 未验证风险 → 判据**

---

## D1 定位 = 自研电控框架的第 0 号垂直切片，不是通用 infra

- **理由**：只有一个真实负载（达妙电机），没有第二个样本时的抽象就是猜；11 月是"启动"不是"做完"，先把一个轴打到能动才有可演示的东西
- **依据**：线档案 §12.2「模块设计是技能不是知识，只能在真实外设上练」「n=1 分不清通用和巧合」（你自己的判断）；AGENTS.md 优先级 ①
- **替代**：直接做 RM 全场景 infra → 要有 DJI/遥控/图传/裁判/RTOS，11 月前出不来，且抽象全靠推演
- **风险**：将来接非达妙设备时，`Device` 接口可能需要改一次
- **判据**：J1 能动 + 保持 <1° + 三类保护（`00-进门先看.md` 五条）

## D2 `SDK_MAX_BUS = 3`，用几路由 `Bus_Create()` 决定

- **理由**：容量 = 硬件能力（事实）；使用数 = 配置（需求）。两者混写就会像我上一轮那样在 2 和 3 之间反复
- **依据**：板载手册 p5「引出 3 路 CAN」、官方例程 `fdcan.h:35-39`（hfdcan1/2/3）
- **代价**：3 路静态池常驻 ≈ 888 B（16 条订阅/路）；不用也占，因为表是编译期数组
- **替代**：按"计划用几路"确定量 → 每次需求变化都要改常量，且丢失"硬件还能再开一路"的信息
- **判据**：`Bus_Create` 第 4 次返回 `NO_RESOURCE`（有测试）

## D3 `SDK_MAX_SUB = 16`

- **理由**：下界可数（6 电机 + 电容 + IMU + 上位机 ≈ 10）→ 向上取 2 的幂 = 16（余量 6 条，写明是余量不是精度）
- **依据**：本文件 D1 的场景；订阅 = 每台**接收设备**一条（共用 Master ID 的 6 轴 = 6 条，不是 1 条）
- **替代**：32（RM 全场景用）→ 白占 512 B/总线且掩盖"实际只需 10 条"
- **风险**：若将来同总线再挂 6 台以上设备，会撞 `NO_RESOURCE`（可观测，非静默）
- **判据**：第 17 条订阅返回 `NO_RESOURCE`；开机 banner 打 `sub=10/16`

## D4 `SDK_MAX_DEV = 8`

- **理由**：6 关节 + 1 外设组 + 1 预留 = 8；一个结构管多通道算一个设备（C620 四通道 = 1）
- **依据**：D1 场景
- **替代**：16 → 无需求
- **风险**：低
- **判据**：第 9 次注册返回 `NO_RESOURCE`

## D5 `SDK_MAX_TASK = 8`

- **理由**：控制 / 下发 / 保护巡检 / 上报 / 遥测 = 5~6 个周期任务 → 取 8
- **依据**：`00-进门先看.md` 阶段 1 需要"超时断使能"（保护巡检）+ "保持"（控制）
- **替代**：16（留调试位）→ 差 8 × 任务项 ≈ 几百字节，非关键；选 8 是为了逼自己别塞任务
- **判据**：第 9 个任务返回 `NO_RESOURCE`

## D6 前注：问询式 ≠ 阻塞式（但你的直觉抓到了实质）

- **不阻塞**：`Bus_Send` 只把帧交进硬件队列就返回；反馈由中断收进 FIFO，主循环取。
  全程没有"等回帧"的等待。
- **但控制帧与反馈是绑定的**（手册 p11：收到匹配帧才回状态）→ 三条后果，必须写进设计：
  1. **下发频率 = 反馈频率**。想持续知道位置，就必须持续发控制帧（哪怕 Kp=Kd=0 的合法 MIT 帧）；
  2. **丢一帧控制 = 同时丢一帧反馈**。"断线检测"因此只能靠「我发了但没回」——这正是 `IsOnline` 的物理依据；
  3. **上电读角度/温度也要发帧**：只在需要时"问一次"不行，验收第 1 条要求周期发帧才看得到数据。

## D6 控制/反馈频率：**先按 200 Hz**（假设，非需求）

- **理由**：达妙反馈是问询式（收一帧控制回一帧），所以下发频率 = 反馈频率 = 总线负载的唯一频率输入；200 Hz 是机械臂位置保持的常见起点
- **依据**：手册 p11「反馈行为为问询式」；200 Hz 本身**无依据，是占位假设**
- **替代**：1 kHz → 六轴 @1 Mbps 会到 156%，且 MCU 侧无必要；50 Hz → 保持品质可能不足
- **风险**：**这是本包最强的未验证假设**。200 Hz 不够时表现为"保持时轻微抖动/回弹"，需要升频或加前馈
- **判据（验收用，不是反推公式）**：固定同一组 Kp/Kd，做频率扫描 50 / 100 / 200 / 500 Hz
  各保持 10 s，记录「静态误差峰峰值 + 抖动幅度」，取**满足 <1° 的最低频率**。
  ⚠️ 注意：误差同时受增益影响，**频率与 Kp/Kd 是耦合的**，扫描时必须固定增益，否则测的是两件事

## D7 波特率：v1 固定 1 Mbps（经典帧），不做 CAN FD

- **理由**：出厂默认 1 Mbps；六轴 200 Hz 双向负载 31%（见 D8），够用；>1 Mbps 电机自动切 CAN FD，反馈走 FD 帧，port 要升级才能收
- **依据**：手册 p11 默认 1 Mbps；p16「大于 1 Mbps 自动变成 CAN FD…上层控制器将接收不到反馈数据」
- **替代**：2 Mbps FD → 负载 15%，但要写 FD 收发，且 FD 反馈帧的 DLC/载荷未知（手册未写，需实测）
- **风险**：**"1 Mbps"目前是手册默认值，未在你这台电机上实测确认**
- **FD 帧格式：手册确实没写（已全文检索证实）** —— 关键词 `CANFD / CAN FD / BRS / DLC / 64 字节 /
  数据场 / 速率切换` 扫 45 页，命中只有 p16 那一句「大于 1 Mbps 自动变成 CAN FD」，
  **没有任何 FD 帧格式章节**。所以 FD 反馈帧的 DLC / 载荷 / 是否 BRS = 只能实测
- **FD 实测的前提**：经典版 USB2CAN 收不到 FD 帧 → 必须用 MC02 自己的 FDCAN 做，属上板任务
- **判据**：上板抓到反馈帧即为确认（L3）；抓不到就先怀疑波特率

## D8 总线负载红线：目标 ≤50%，硬上限 70%

- **理由**：负载率是"能不能挂、要不要分路"的唯一判据；>70% 时排队延迟开始不可预测
- **依据**：CAN 工程惯例（非手册）；本场景实测值 31%（6 轴 × 200 Hz × 2 帧 × 130 µs）
- **替代**：不设红线 → 现场表现为偶发 `tx_busy`，查不出原因
- **风险**：31% 是**理论估算**，实际含位填充/重发/错误帧会更高
- **判据**：L4 = 上板后 `BusStats.tx_busy` 在 10 分钟内保持 0

## D9 取整规则：向上取 2 的幂；禁止小数系数

- **理由**：小数系数（如 1.45/1.6）看起来像推导、实际是拍；2 的幂的"下一个可用值"是明确的，且位运算/缓存友好
- **依据**：你在 `config.h` R21/R28 的两条 review 指出的问题
- **代价**：比"精确值"浪费一点（如 10 → 16）
- **判据**：config.h 里出现任何非整数倍系数 = 规范违反

## D10 撤掉 `SDK_PROFILE_FULL`，写明升级触发条件

- **理由**：无需求的双档 = YAGNI 违反；且"支持两种定位"等于没定位
- **依据**：D1 + 你「前身我认」
- **替代**：保留 FULL → 多一整套不被任何用例验证的常量
- **升级触发（三者任一）**：① 出现 ≥1 个非达妙真实设备 ② 出现第 2 条真实总线需求 ③ 有外部使用者要用
- **判据**：触发发生前，`config.h` 里只有一档
